# 发布与验收流程

## 持续集成边界

[CI workflow](../.github/workflows/ci.yml) 在每次推送 `main` 和 Pull Request 时执行：

1. 在 Ubuntu 与 Windows 的 Python 3.10、3.11、3.12、3.13 上安装包。
2. 运行单元测试及默认禁用的真机集成测试。
3. 构建 wheel 并上传为 workflow artifact。

工作流中的官方 Actions 固定到完整 commit SHA，`.github/dependabot.yml` 每周检查 `github-actions` 更新并提交 Pull Request，避免长期停留在旧运行时，同时不依赖可变主版本标签。

GitHub Actions 不持有真实设备、`tests/integration.json`、设备服务密码或 `iproxy`。因此它只能证明客户端行为和打包质量，不能替代真机验收。

## 本地发布检查

发布检查示例统一使用标准写法 `python`（系统只有 `python3` 时替换同名命令）。冒烟测试由跨平台脚本 `scripts/smoke.py` 负责，Windows 可继续用薄包装 `scripts\windows-smoke.ps1`，两个平台共用同一份校验与运行逻辑。

发布人应在合并前执行：

```bat
python -m unittest discover -s tests -v
python -m pip install --user --upgrade .
python -m uitap status
```

再执行配置化只读真机 smoke：

```bat
copy tests\integration.example.json tests\integration.json
edit tests\integration.json
python scripts/smoke.py --install
```

Windows 也可等价的用包装脚本（自动优先 `py`，否则用 `python`）：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\windows-smoke.ps1 -Install
```

`tests/integration.json` 必须有：

- 正确的目标地址或 USB 回环地址；
- `enabled: true`；
- 当前目标 App 中唯一、经过 Inspector 验证的 `expected_selector`。

该脚本不会点击、输入、上传、删除、运行项目或执行 `eval`。它生成的 `artifacts/integration/<timestamp>` 应作为发布证据保存。

## 版本策略

- 补丁版本：修复缺陷、文档纠正、无行为扩展的小改动。
- 次版本：增加向后兼容的公开 API、命令或配置字段。
- 主版本：破坏现有公开 API、配置格式或 CLI 默认行为时才使用。

每个版本必须同步更新三处：`pyproject.toml` 的 `project.version`、[变更说明](变更说明.md) 的 `## X.Y.Z` 小节、以及 [API 使用参考](API使用参考.md) 首部版本声明。不要仅修改 wheel 文件名或手工修改 `site-packages`。

三处同步由工具强制，不依赖人工记忆：

- `python scripts/version_sync.py`：本地随时校验，不一致时返回码 `1`；
- `tests/test_release_metadata.py`：每次 CI 推送与 PR 都会运行，漏改即在合并前失败；
- `python scripts/verify-release-tag.py vX.Y.Z`：发布工作流 validate 阶段先校验 tag 与包版本一致，再校验三处同步，任一处不符都会终止发布。

## 发布步骤

1. 确认工作区干净，审阅变更和文档。
2. 运行 CI 对应的本地单元测试。
3. 在至少一台目标 iPhone 上完成 smoke，并保留工件。
4. 更新三处版本（`pyproject.toml`、`docs/变更说明.md`、`docs/API使用参考.md`）与兼容性矩阵，然后执行 `python scripts/version_sync.py` 确认一致。
5. 合并到 `main`，确认 GitHub Actions 通过。
6. 使用已验证提交创建与包版本一致的 Git tag，例如包版本 `0.1.0` 对应 `v0.1.0`。推送 tag 后，[Release workflow](../.github/workflows/release.yml) 会重新运行 Ubuntu/Windows、Python 3.10 至 3.13 验证，构建 wheel 与 sdist，生成 `SHA256SUMS`，创建 GitHub Release，并通过 Trusted Publishing 把同一构建发布到 PyPI。
7. 确认 GitHub Release 的 wheel、sdist 和校验文件完整，再在 Windows 从新克隆或干净虚拟环境执行安装验证。
8. 在目标真机运行 `python -m uitap doctor --report artifacts\doctor.json`；USB 场景还须完成 `tunnel`、`status` 和 `log` 验收。

Release workflow 会拒绝与 `pyproject.toml` 版本不一致的 tag。发布到 PyPI 使用 Trusted Publishing：首次发布前需在 PyPI 项目（uitap）的 Publishing 页添加发布者——仓库 `CoconutHR/uitap`、工作流 `release.yml`；未配置时 PyPI 发布步骤会失败，但不影响已创建的 GitHub Release。已有 tag 不会因工作流后来加入而追溯触发，也不应通过删除后重推 tag 来补发。

## 回滚

客户端回滚不需要修改 IPA：

```bat
git checkout <last-known-good-commit-or-tag>
python -m pip install --user --upgrade .
python -m uitap status
```

记录失败版本、设备/设备服务/目标 App 版本、`manifest.json`、截图、XML、日志及命令输出。回滚后不要删除失败证据。
